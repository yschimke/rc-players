# Conformance corpus: expectations to push back on

The running list of golds and format rules this repository thinks are wrong or underspecified,
with the evidence for each. It is the third outcome in
[`RC_CONFORMANCE.md` → never trade the player for a number](RC_CONFORMANCE.md#the-rule-never-trade-the-player-for-a-number):
*the corpus is asserting something a player cannot or should not reproduce — record it, raise it
upstream, and let the check keep failing.*

Measured against patch set 2 of
[4302372](https://android-review.googlesource.com/c/platform/frameworks/support/+/4302372)
(`bf2ca73`, 364 golds), as vendored on `vendor/androidx-rc-conformance`. An entry leaves this file
when upstream fixes it or when we find we were wrong. Each one says which of those would settle it.

## 1. Twenty golds were written by the TypeScript player, not generated by AndroidX

The corpus says its golds come from AndroidX's own engine, and
[`RC_CONFORMANCE.md`](RC_CONFORMANCE.md#the-reference-is-the-corpus-not-another-player) relies on
that. These twenty do not. `generate-expanded-corpus.mjs` builds their documents with the
TypeScript player's `RemoteComposeBuffer`, loaded from a hard-coded path on one developer's machine
(`.../remotecompose-experiments/players/typescript`), and records that player's answers as the
expectations.

`canvas_clip_path_and_skew`, `canvas_draw_bitmap_and_offscreen`, `canvas_draw_text_run_and_content`,
`data_id_lookup_indirection`, `expr_rpn_comprehensive_float_operators`,
`interactivity_touch_down_up_cancel`, `interactivity_value_string_and_int_actions`,
`loom_macro_block_slot_injection`, `loom_macro_parameter_remapping`, `matrix_3d_pipeline_operations`,
`matrix_from_path_tangent_frame`, `particle_attractor_radial_field`,
`particle_compare_conditional_respawn`, `path_draw_tween_path_render`,
`path_expression_polar_parametric`, `path_expression_wave_oscillator`,
`path_tween_morph_interpolation`, `text_style_and_layout_text`,
`wire_component_value_and_custom_layout`, `wire_id_lookup_table`.

The rest of the corpus bears the difference out. The TypeScript run passes all twenty. The CMP player
refuses every document. AndroidX's own JVM player refuses 13 and fails the other 7. The native Swift
player loads all twenty and still fails 19 of them on the value check. Several documents are not
valid by AndroidX's wire format:

| gold | defect | evidence |
| --- | --- | --- |
| `path_expression_wave_oscillator`, `path_expression_polar_parametric` | `PathExpression.count` is written as the raw int `0x00000010`. AndroidX writes that field as a float word (it can be a variable reference), so it decodes as 2.2e-44, truncates to 0, and the path is empty. | Bytes after opcode `0xc1`: `id=16, flags=1, min=0.0, max=1.0, count=00 00 00 10` |
| `expr_rpn_comprehensive_float_operators` | A `FloatExpression` of 43 words. AndroidX's reader caps an expression at 32. | AndroidX's JVM player errors with `Float expression too long`, the same message as the CMP decoder |
| `interactivity_value_string_and_int_actions` | A `ValueStringChangeAction` whose value is text 63, which the document never defines. | Document defines only text 62 (`InitialText`) |
| `data_id_lookup_indirection` | An `IdLookup` whose collection is id 54, which is a `TextData` rather than a list. | Bytes: `DATA_TEXT 54 "TargetString"`, then `ID_LOOKUP 55 ← 54[0]` |

**Ask:** regenerate these through AndroidX's generator (`ConformanceGoldGeneratorTest`), as with the
rest of the corpus, or mark them as TypeScript-sourced so that runners can score them separately.
**Settled by:** a regenerated set, or a statement that these documents are meant to be valid.

## 2. `ops:*` never says which operation names it asserts, and the corpus uses three sets

`CONFORMANCE_FORMAT.md` gives `ops:present` as `["DrawRect", …]` and says nothing about which
vocabulary those names come from. The golds use three:

* **AndroidX's concrete class names**, most of the time: `ShaderData` (opcode 45, constant
  `DATA_SHADER`), `TimeAttribute` (`ATTRIBUTE_TIME`), `ImpulseOperation` (`IMPULSE_START`),
  `PathData`, `ColorExpression`, `LoopOperation`. These are the names in the registry's
  `androidJavaClass`, and every one of them is a class in `remote-core` alpha19.
* **AndroidX's constant-derived name, where the class differs**: the eight `semantics_*` golds assert
  `AccessibilitySemantics`. Opcode 250's class is `CoreSemantics`, and `AccessibilitySemantics` is
  only an interface.
* **Names only the TypeScript player uses**, in seven golds: `TouchDownModifier`, `TouchUpModifier`,
  `TouchCancelModifier`, `RippleModifier`, `DrawContentModifier`, `DimensionConstraintsModifier`,
  `CanvasOperationsOp`, `ParticlesCompareOp`, `Matrix3DOp` and the other 3D names, and
  `DrawTextOnCircleStub`. The `Stub` suffix makes it plain that this is an implementation detail
  leaking into a cross-player assertion.

Of 87 distinct names the corpus asserts, 67 are AndroidX class names and 16 exist only in the
TypeScript player. More than half of all opcodes (90 of the 172 in our manifest) have a class name
that differs from their constant.

This lane now reports both AndroidX names for each operation (see `CmpEngine.censusNames`). That
brought 44 golds from failing to passing, and nothing regressed. The TypeScript-only names are left
failing on purpose.

**Ask:** state that `ops:*` and `records:components` use AndroidX's concrete class simple name, which
is `androidJavaClass` in `operations-registry.json`, and regenerate the seven golds.
**Settled by:** a stated vocabulary.

## 3. `matrix_3d_pipeline_operations` is in the core profile but tests a TypeScript extension

It asserts `DefineMesh3D`, `SetCamera3D`, `Matrix3DOp`, `DrawMesh3D`, `Paint3DState`, `SetLights3D`
and `VectorExpression`. The corpus's own `operations-registry.json` counts those opcodes under
`playerExtension3d` and not as AndroidX operations. AndroidX's JVM player errors with
`Unknown operation encountered 110`.

**Ask:** move it to the `extended` profile, or drop it.

## 4. `expr_integer_bitwise_ops` has no expressions in it

The document is 73 bytes: the header and a name. It contains no `IntegerExpression`, yet the gold
asserts that integer slots 201 to 208 are all 0. It cannot test bitwise operations, and a player can
pass it only by reading slots it never wrote as 0. The CMP lane reports those slots as unwritten, and
that is correct.

**Ask:** regenerate it. The expressions appear to have been dropped during generation.

## 5. `clock_snapshot`'s `clock` object is not specified

Section 3 says to "rebuild the whole document against a frozen clock". The golds write that clock
in three different shapes, and none of them is documented:

* `{"timestamp_millis": 1789050600000}`, an instant;
* `{"hour": 10, "minute": 10, "second": 30}`, a time of day with no date;
* `{"continuous_seconds": 15.5}`, seconds on the clock face.

None of them names a time zone. This lane reads all three as wall-clock time in UTC. UTC is the only
zone that makes `clock_digital_calendar` consistent with its own `parameters.fixedTimestamp`. Before
this change the lane treated `continuous_seconds` as animation time. Both snapshots of
`clock_analog_hands` then reported identical hands.

**Ask:** document the three shapes and the zone.

## 6. `frame_sequence.base_time_millis` is ambiguous

Section 3 says frames are 1/60 s apart. It does not say whether `base_time_millis` is the clock's
reading at frame 0 or a time the runner should move to. Moving the clock to it (10 s after a resize
trigger) completes every layout animation before the first capture. Only differences between times
are observable, so reading it as the timestamp of frame 0 is the only interpretation that works. The
spec should also say **one frame per step**. A millisecond clock that rounds up to whole frames runs
two frames on some steps. That made all eight particle golds fail, until this lane switched to one
frame per step.

**Ask:** document both points.

## 7. Advisory flags on raster checks look inconsistent

612 raster checks are marked `"advisory": true` and 21 are not. Some of the 21 are clearly deliberate,
such as the `canvas_*` primitives. Others look like a missed flag within a single gold:
`clock_digital_calendar` marks its `initial` raster advisory but not its `snap_0` one, and
`clock_analog_hands` leaves both snapshots binding.

**Ask:** confirm that the 21 are intended.

## 8. `conditional_skip_api_gate` assumes API level 7, but AndroidX is on level 8

The gold says it exercises each `Skip` comparison "against the player's API level 7". AndroidX alpha19
reports `CoreDocument.DOCUMENT_API_LEVEL = 8`, and so does this player's decoder, so the
`api_equal_to` and `api_not_equal_to` gates resolve the other way. The census failures that follow
(`DrawLine` present, `DrawArc` absent) come from the gold's API level being stale, not from how the
player skips.

**Ask:** regenerate against the current level, or have the gold state which level it assumes so a
runner can decode at that level.

## 9. `interactivity_hit_testing_bounds` hit-tests a box where it is not drawn

The box is 100×60, with an offset modifier of (50, 50). The gold expects a tap at (50, 30), in empty
space above the drawn box, to be handled, and a tap at (50, 80), on the drawn box, not to be. AndroidX
tests the component's layout rectangle and leaves out the offset it paints with. This player
hit-tests where it draws, which is what a user tapping the box expects.

**Ask:** confirm whether ignoring the offset is intended. If it is not, fix the reference and
regenerate. If it is, the spec should say that hit testing ignores offset modifiers.

## 10. Question: `click` delivered at once, even with a double-click handler

With a `MultiClickModifier` that has a double-click action, this player (like Android's View player)
waits the double-tap timeout before it confirms a single click. The reference delivers the click
immediately. `modifier_multi_click` then reads the tree at the frame of the click and sees the
change not yet applied. Every host that tells a single click from a double one has this delay, so we
treat it as host behaviour. It is recorded here in case the corpus means something stronger.

**Not yet raised.**

## 11. Question: mid-animation layout geometry as a binding check

The five `animation_*` golds check tree geometry at sampled frames of a layout transition. For
example, `animation_box_offset` expects progress 0.497 at frame 5 and 0.999 at frame 10. That ties a
player to AndroidX's exact duration and easing curve. Now that this lane actually drives those
frames (§6), the CMP player's transition is measurably slower: 0.28 at frame 5 and 0.81 at frame 10.
Frame 18 matches. We are treating this as **a finding about the player** until shown otherwise, but
it is worth asking whether mid-transition frames should bind, or carry a tolerance.

Settled on our side since: the gold is not reproducible from the spec the document declares.
`animation_box_offset` declares 300 ms with `CUBIC_STANDARD` (0.4, 0, 0.2, 1). At 60 fps, frame 5 is
t = 0.28 and frame 10 is t = 0.56, which gives progress 0.28 and 0.815. That is exactly what this
player now reports. The gold's 0.497 and 0.999 need t = 0.349 and t = 0.952. No uniform frame clock
produces both from the declared easing, so the gold is recording AndroidX's own frame sampling, not
the animation the document asks for.

**Ask:** make mid-transition layout checks advisory, or record them from a clock that advances 1/60 s
per frame.

## 12. Value checks that read back the document's own constant

These entries came out of the native-appkit review of the 2026-09-23 run (`ee18643`).

**Golds:** the eight `scheduling_*` and eight `semantics_*` golds with a `float` check;
`data_boolean_constant_and_lookup`, `data_long_constant_and_lookup`,
`wire_boolean_and_long_primitives`, `wire_debug_message_emission`,
`wire_sound_data_and_play_sound`.

Each carries one value check besides `ops:present`, and that check cannot see the operation under
test: the asserted float is a `FloatConstant` the document declares beside it. For example,
`scheduling_impulse_process_body` asserts slot 110 = 2, and its first operation is
`FloatConstant(110, 2.0)`. The semantics golds write the role number they declare into their marker
slot, and several golds use the opcode number itself as the marker. The impulse window, the long's
value, the boolean's value and the semantics node are never asserted, so a player that parses these
operations and ignores them passes. The corpus's §1 says an assertion that cannot fail is worse than
none.

**Ask:** assert the operation's own effect — the impulse body inside and outside its window, the
long and boolean values through a typed probe, debug and sound as recorded events.
**Settled by:** checks that fail for a parse-only implementation.

## 13. `clock_time_attribute_from_load` tests the month

Its `TimeAttribute` uses type 10, `TIME_MONTH_VALUE`, and expects 10 (November, zero-based).
`TIME_FROM_LOAD_SEC` is type 14, and no gold tests it.

**Ask:** rename this gold, and add one for `TIME_FROM_LOAD_SEC`.

## 14. Clock golds with no `clock_snapshot` still depend on the host's zone

`clock_time_attribute_calendar_date` and `clock_time_attribute_day_of_week` read the instant
1 700 000 000 000 ms, 2023-11-14T22:13:20Z, from a `LongConstant`, and expect day 14 and weekday 1
(Tuesday). The reference reads calendar fields in the system zone, and in any zone 1 h 47 min or more
east of UTC that instant is the 15th, a Wednesday. §5's missing zone applies here too, with no
`clock_snapshot` step to hang it on.

**Ask:** declare the zone in `harness`, or pick an instant near midday UTC.

## 15. `text_attribute_and_transform` cannot fail

It asserts 110.7421875 for the width of "TransformSample". That depends on the font, and the harness
declares no `text_metrics`. It also carries `"tolerance": 1000`, so any value from −890 to 1111
passes — including the 0 a player with no text metrics reports.

**Ask:** declare `text_metrics: "ahem"` and a real tolerance, or assert the length selector.

## 16. `colortheme_theme_light_dark_switch` sets no theme and switches nothing

Its document is `THEME(1)` followed by one `ColorConstant`. AndroidX's themes are `UNSPECIFIED` (-1),
`DARK` (-2) and `LIGHT` (-3); 1 is none of them, and the timeline is a single paint, so nothing
switches. The check asserts the constant's own value.

**Ask:** use `THEME_DARK`/`THEME_LIGHT`, and add `theme` steps as `color_theme_mode_switching` does.

## 17. `matrix_constant_3x3_and_4x4` expands a 3×3 matrix inconsistently

The gold declares the 3×3 matrix `[2, 0, 5, 0, 3, 7, 0, 0, 1]` and applies it to `(1, 1, 0)` with
`MATRIX_VECTOR_MATH` type 0, which adds each row's translation. It expects `(7, 3, 0)`: row 0 adds
its translation (2 + 5 = 7) and row 1 does not (3, not 3 + 7). No single reading of a 3×3 affine
matrix gives that. The standard embedding gives `(7, 10, 0)`. The expected values come from an
embedding that puts the third column in the translation slot for row 0 and in the z column for
row 1, and the CMP and TypeScript players both implement that embedding. The native player keeps
the standard embedding and fails this check.

**Ask:** state how a 3×3 `MATRIX_CONSTANT` maps to the 4×4 that `MATRIX_VECTOR_MATH` multiplies by,
or use a 4×4 matrix in this gold.
**Settled by:** a stated layout. If upstream says the asymmetric one is intended, the native player
adopts it.
