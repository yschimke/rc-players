# Conformance pushback log

Golds and expectations in the AndroidX conformance corpus that we think are wrong, weaker than they
look, or asking for something a player should not have to reproduce. Each entry is a candidate for an
upstream comment on the corpus change, and each has been checked against the corpus as vendored on
`vendor/androidx-rc-conformance`, not taken from a lane's failure alone.

What an entry here does **not** mean: that the check is skipped or scored as a pass. Per
[`RC_CONFORMANCE.md`](RC_CONFORMANCE.md#the-rule-never-trade-the-player-for-a-number), a check we
dispute keeps failing if the player fails it, and the player is never bent to satisfy it. Where we
did change something to match a gold anyway, the entry says so and why.

Entries were first collected from the native-appkit review of the 2026-09-23 run (`ee18643`).

## 1. The `ops` vocabulary is one implementation's class names

**Golds:** every gold with an `ops:present`, `ops:absent` or `ops:counts` check — 84 distinct names
across the corpus.

The `ops` probes compare operations by *name*, and the names the golds use are the class names of the
corpus's TypeScript player, not AndroidX's. The corpus's own `operations-registry.json` records both,
and for 46 of the 162 AndroidX-active opcodes they differ. In every divergent case the golds assert
the TypeScript name:

| opcode | AndroidX class | asserted by the golds |
| --- | --- | --- |
| 250 `ACCESSIBILITY_SEMANTICS` | `CoreSemantics` | `AccessibilitySemantics` |
| 173 `CANVAS_OPERATIONS` | `CanvasOperations` | `CanvasOperationsOp` |
| 194 `PARTICLE_COMPARE` | `ParticlesCompare` | `ParticlesCompareOp` |
| 219 `MODIFIER_TOUCH_DOWN` | `TouchDownModifierOperation` | `TouchDownModifier` |
| 229 `MODIFIER_RIPPLE` | `RippleModifierOperation` | `RippleModifier` |
| 57 `DRAW_TEXT_ON_CIRCLE` | — (not in AndroidX's reader) | `DrawTextOnCircleStub` |

The rest are the same pattern: the `…ModifierOperation` family loses its suffix, and parse-only
TypeScript classes are asserted under their `…Stub` names.

**Why it matters.** The corpus describes itself as language-neutral and generated by AndroidX's own
engine, but a player can only pass these checks by learning another player's internal class names —
including names that announce the class is a stub. AndroidX's own Java class names would fail them.

**Proposed upstream:** assert opcodes, or the `AREA-02` constant names (`ACCESSIBILITY_SEMANTICS`),
which are the wire protocol's own vocabulary.

**What we did:** the native-appkit census reports the golds' names, because the probe compares
strings and that lane's draw log already did the same (`DrawTextOnCircleStub`). The CMP lane derives
names from the AndroidX constant instead (`DATA_SHADER` becomes `DataShader`, where the golds say
`ShaderData`), so it disagrees with the golds on a different set of rows. Both lanes change if
upstream moves to opcodes.

## 2. A core-profile gold asserts opcodes AndroidX does not define

**Gold:** `matrix_3d_pipeline_operations` (core profile).

It asserts `DefineMesh3D`, `SetCamera3D`, `Matrix3DOp`, `DrawMesh3D`, `Paint3DState`, `SetLights3D`
and `VectorExpression` — opcodes 110–116. The corpus's registry marks all seven
`PLAYER_EXTENSION_3D`, with no AndroidX class. `rc-player-protocol`'s `RcOpcodes`, which tracks
AndroidX's `Operations` registry, has none of them.

**Proposed upstream:** move it to the extended profile, or drop it until the operations exist in
AndroidX.

## 3. Value checks that read back the document's own constant

**Golds:** the eight `scheduling_*` and eight `semantics_*` golds with a `float` check;
`data_boolean_constant_and_lookup`, `data_long_constant_and_lookup`,
`wire_boolean_and_long_primitives`, `wire_debug_message_emission`, `wire_sound_data_and_play_sound`,
`wire_id_lookup_table`.

Each of these carries one value check besides `ops:present`, and that check cannot see the operation
under test: the asserted float is a `FloatConstant` the document declares beside the operation. For
example, `scheduling_impulse_process_body` asserts slot 110 = 2, and its first operation is
`FloatConstant(110, 2.0)`. The semantics golds write the role number they declare into their marker
slot, and several golds use the opcode number itself (`wire_id_lookup_table` asserts 192, which is
`ID_LOOKUP`). The impulse window, the long's value, the boolean's value, the semantics node and the
lookup's output are never asserted.

So an implementation that parses these operations and ignores them passes every one of these golds.
The corpus's §1 says an assertion that cannot fail is worse than none. The TypeScript player's own
`TimeAttribute` port calls a parse-only stub "the most expensive kind of gap", and these golds are
the ones that cannot catch it.

**Proposed upstream:** assert the operation's own effect — the impulse body inside and outside its
window, the long/boolean value through a typed probe, the lookup's output id, and debug and sound as
recorded events.

**What we did:** the native core now decodes long and boolean constants, debug messages and the sound
family, because refusing the whole document over them was a real player bug. It still refuses the
impulse and `WAKE_IN` operations instead of stubbing them to pass the scheduling golds.

## 4. `IdLookup` golds do not look anything up

**Golds:** `data_id_lookup_indirection`, `wire_id_lookup_table`.

Both documents point `IdLookup`'s `listId` at a `TextData` (54 and 10) rather than an id list, so
there is no list to index. `data_id_lookup_indirection` then checks `text` at 54 — the source string,
not the lookup's output at 55. Neither gold exercises the operation it names.

**Proposed upstream:** declare a real `DataListIds`, and assert the output id.

## 5. `clock_time_attribute_from_load` tests the month

**Gold:** `clock_time_attribute_from_load`.

Its `TimeAttribute` uses type 10, `TIME_MONTH_VALUE`, and expects 10 (November, zero-based).
`TIME_FROM_LOAD_SEC` is type 14. No gold tests type 14 at all.

**Proposed upstream:** rename this gold, and add one for `TIME_FROM_LOAD_SEC`.

## 6. Clock golds depend on an undeclared time zone

**Golds:** `clock_time_attribute_calendar_date`, `clock_time_attribute_day_of_week`.

Both read an instant 1 700 000 000 000 ms, 2023-11-14T22:13:20Z, and expect day 14 and weekday 1
(Tuesday). The reference reads the fields in the system zone. In any zone 1 h 47 min or more east of
UTC, that instant is already the 15th, a Wednesday. These golds pass only on a UTC host, and the
harness does not declare a zone.

**Proposed upstream:** add a time zone to `harness`, or pick an instant near midday UTC.

## 7. A text width asserted without a declared font model

**Gold:** `text_attribute_and_transform`.

It asserts 110.7421875 for a measured attribute of "TransformSample". The value depends on the font,
but the harness declares no `text_metrics`, unlike the golds that use the Ahem model to make width
portable. It also carries `"tolerance": 1000`, so any value from −890 to 1111 passes — including the
0 a player with no text metrics at all reports. The check cannot fail.

**Proposed upstream:** declare `text_metrics: "ahem"`, or assert a font-independent attribute such
as length.

## 8. A layout component with no root

**Gold:** `text_style_and_layout_text`.

Its document is a `TextStyle`, then a `TextLayout` component at top level with no
`RootLayoutComponent` around it, then the `FloatConstant` its value check reads (143 = 18). The
spec does not say what a layout component outside a root means; the CMP player refuses it
("Layout component appears outside a RootLayoutComponent"), and so does the native core. The only
value asserted is the constant.

**Proposed upstream:** put the text in a root, and assert something the style changes — the laid-out
height, or the resolved size in a `records` probe.

**What we did:** the native core now decodes `TextStyle` and applies it to `CoreText` through its
parent chain, and renders an unknown `TextLayout` overflow as clip as AndroidX does. It still refuses
a layout component outside a root.

## 9. `colortheme_theme_light_dark_switch` sets no theme and switches nothing

**Gold:** `colortheme_theme_light_dark_switch`.

Its document is `THEME(1)` followed by one `ColorConstant`. AndroidX's themes are `UNSPECIFIED` (-1),
`DARK` (-2) and `LIGHT` (-3); 1 is none of them, and the timeline has a single paint step, so nothing
switches. The check asserts the constant's own value.

**Proposed upstream:** use `THEME_DARK`/`THEME_LIGHT`, and add `theme` steps as
`color_theme_mode_switching` does.

## Minor, noted rather than disputed

* `clock_digital_calendar` expects `cal_epoch` = 1 789 050 624 for an instant of 1 789 050 600 s.
  That is the value after rounding to a float32, the precision of a float slot. It is deterministic
  and correct for a float32 slot, but a player that keeps wider slots would fail it for being more
  precise. A stated tolerance would say which precision is intended.
