# Version-dependent writes, and their counterparts in `rc-player-edit`

The creation writer does not write the same content the same way for every player. Some of that is
the profile's operation table (an operation the profile lacks is refused, or replaced by an older
one); some is the document API level (what level 6 has no header for, what level 7 draws differently
from level 8); some is a feature tag a surface asks for. A document written for a higher level and
rewritten by `rc-player-edit` for a lower one has to get what the writer would have written for the
lower one, or be refused with a reason. This page lists every such write we found, where it is, what
the edit module does about it, and how each was checked.

"Writer" is `third_party/remote-creation-writer` (`RemoteDocumentWriter.kt`, `Profile.kt`),
"compose" is `third_party/remote-creation-compose/compose/upstream/remote-creation-compose/src/jvmAndAndroidMain/kotlin/ee/schimke/composeai/rccreation/compose`,
"upstream" is AndroidX `androidx-main` (`/compose/remote/…`; `RCW` is `RemoteComposeWriter.java`,
`RCB` is `RemoteComposeBuffer.java` in `remote-core`). Levels: 6 is Android 16's platform player, 7
is Android 17's and AndroidX alpha22's level 7, 8 is AndroidX's current level. Every document the
writer writes has header version 1.1 at levels 7, 8 and 9 (`MINOR_VERSION` is 1 upstream too; 1.2 is
written only for a document with a custom component), so the profile bits and the operations, not
the version, tell a level 7 document from a level 8 one; `RcHeader.apiLevel` reads 1.1 as 7.

## What the edit module does for a document going down

`adaptTo(target)` applies, in order: macro inlining, `CoreText` to `TextLayout`, theme colours,
wall-clock animation, remark dropping, the caller's unsupported-operation policy, **`CanvasContent`
and the canvas `ComponentValue` ids (3, 4)**, **the legacy border (5)**, density baking, spacing
literals, literal float fields and colours, and the header (6, 7, 9, 10). It returns what it could not
make right in `violations`. Down to level 7 or 6 these now include a density behaviour, scroll
directions, a path winding rule and a glyph spacing, none of which a rewrite can keep the meaning of,
each naming the feature and the target.

Going up (level 6 or 7 to 8) nothing is lost: a level 8 player reads the legacy header, a
`CanvasContent` and a legacy border as they are, so an adaptation changes the header only, and only
where a profile or a level 6 header with density-scaled sizes needs it (9).

## Not done, and why

* **Font axis (16).** Replicating it needs a paint bundle decoder in `rc-player-edit` and gains nothing
  we could observe on the players we can run.
* **`WidgetsProfileWriterV6`'s substitutions (20).** Whether Android 16 resolves
  `android.textColorPrimary`, or draws without a root behaviour, was not measured.
* **`platformWidgetDocument` in Kotlin (21).** It is Android's `RemoteComposeBuffer` round trip; a
  pure-Kotlin port would let a server do it.
* **`RcHeader.apiLevel` and re-declared headers.** `adaptTo` writes version `1.(level - 6)` when it
  re-declares a header (1.2 for level 8), where the writer writes 1.1 for every level and 1.2 only for
  a custom component. Not changed here; not shown to matter.
